I Ran Qwen3 0.6B Locally in Pure C: Every Operation From Token to Output

There’s a particular kind of satisfaction in watching an LLM generate text on your machine and knowing exactly what’s happening. No Python. No HuggingFace. No magic abstractions. Just C, a model file, and a terminal.

This post walks through what I learned doing that. I ran Qwen3 0.6B locally and traced every step from the moment you type something in to the moment a token comes out.

Why Pure C?

Python hides too much. When you call model.generate() in a library, you get tokens back. You don’t get to see what the KV cache is doing, how sampling works, or why changing temperature changes the output. C forces you to be explicit about everything.

Also, Qwen3 0.6B fits in about 600MB at Q4 quantization and runs on a regular laptop CPU. No GPU needed. That made this whole thing possible.

The Model: Qwen3 0.6B

Qwen3 is Alibaba’s third-generation LLM family. The 0.6B version is the smallest, with 600 million parameters. It uses the transformer architecture, runs in a decoder-only mode, and follows the ChatML prompt format.

At Q4 quantization via GGUF it weighs around 600MB, handles up to 32k tokens of context, and is fast enough on CPU to actually use. Good size for tinkering.

Reading the Model File: GGUF vs SafeTensors

Before anything runs, you load the model off disk. Two formats come up constantly.

SafeTensors is HuggingFace’s format. It’s clean and safe to load, but it stores weights at full or half precision. A 0.6B model at full precision is around 2.4GB. That’s too big for what I was doing.

GGUF is the format used by llama.cpp. It was designed specifically for running models locally on regular hardware. The key feature is built-in quantization support. At Q4 (4-bit weights), the same 0.6B model is around 600MB. You lose a little quality, but for most tasks it’s barely noticeable.

A GGUF file has three parts: a header that identifies the file format, a metadata section that describes the model (number of layers, vocabulary size, context length, etc.), and the actual weight data. Reading it in C is straightforward once you understand the layout.

Tokenization: Turning Text Into Numbers

Models don’t read text. They read numbers. Tokenization is the step that converts your input string into a list of integers.

The approach Qwen3 uses is called BPE (Byte Pair Encoding). It works by breaking text into subword pieces. Common words like “the” or “run” are usually one token. Less common words get split up. “tokenization” might become [“token”, “ization”]. Something totally unknown gets broken into small pieces the model has seen before.

Qwen3’s vocabulary has around 150,000 tokens. Each token is just an integer. “What is the capital of France?” might come out as something like [3838, 374, 279, 6864, 315, 9822, 30]. Those numbers get passed into the model.

The vocabulary size is a tradeoff. Bigger means better coverage and shorter sequences, but more memory for the embedding table.

Chat Templates: How the Model Knows You’re Talking to It

Raw text in doesn’t work well. The model was trained to expect a specific conversation format called ChatML. It looks like this:

<|im_start|>system
You are a helpful assistant.
<|im_end|>
<|im_start|>user
What is the capital of France?
<|im_end|>
<|im_start|>assistant

The <|im_start|> and <|im_end|> tokens are special. The tokenizer treats them as single units, not individual characters. They tell the model who’s speaking and where turns begin and end.

The trick is leaving the assistant turn open at the end. That tells the model “generate from here.” Everything after that is completion.

Get the format slightly wrong and the model either stops making sense or starts generating the prompt back at you. These tokens are load-bearing.

The Transformer: A Plain English Version

This is where the actual computation happens. You have a list of token integers. The transformer turns them into a probability distribution over what comes next.

Here’s the short version of what happens inside:

Each token ID gets looked up in an embedding table, which gives you a vector of numbers representing that token. Those vectors go through 28 layers. Each layer has two parts: attention (which lets tokens look at other tokens in context) and a feed-forward network (which processes each token independently).

Attention is what makes transformers powerful. Every token can look at every previous token and decide how much it matters. When the model is figuring out what “it” refers to in a sentence, attention is doing that work.

After 28 layers, you get one final vector per position, and you multiply it against the vocabulary to get a score for every possible next token. Those scores are called logits. Higher score means the model thinks that token is more likely to come next.

Qwen3 specifically uses a few architectural choices worth knowing: RMSNorm for layer normalization, Rotary Positional Encoding (RoPE) so the model understands token order, and Grouped Query Attention which cuts KV cache memory roughly in half.

The KV Cache: Why Generation Doesn’t Get Slower Per Token

One thing that confused me early on is why generating token 100 doesn’t take 100 times longer than generating token 1.

The answer is the KV cache. During attention, each token produces a key and value vector for every layer. Instead of recomputing those for every token on every step, the model stores them. When generating token 101, you only compute new keys and values for that token. Everything else is already cached.

For Qwen3 0.6B at a 2048-token context, the KV cache is around 117MB. Not trivial, and it grows with context length. For larger models with long contexts, the cache is often what limits how much you can fit in memory.

Temperature and Top-p: Controlling Randomness

After the transformer runs, you have a logit score for every token in the vocabulary. You need to pick one.

The naive approach is just taking the highest score every time. That works but produces repetitive, predictable output.

Temperature is a knob that adjusts how spread out the probabilities are. Low temperature makes the model more likely to pick the obvious next word. High temperature makes it more likely to pick something surprising. I found 0.7 to 0.8 to work well for Qwen3 0.6B.

Top-p (nucleus sampling) is a filter that says: only sample from the tokens that together account for p% of the probability. At top-p 0.9, you’re ignoring the long tail of unlikely tokens. This keeps output sensible while still allowing variety.

These two settings interact. Low temperature plus low top-p gives focused, conservative output. High temperature plus high top-p gives diverse, sometimes chaotic output. Most people run both at moderate values and tweak from there.

The Generation Loop

Putting it all together, generation has two phases.

First, prefill. You format the conversation using the ChatML template, tokenize it, and run the full sequence through the transformer. This fills the KV cache for all your input tokens. You’re not generating yet, just processing the prompt.

Second, the generation loop. You run one forward pass per token. Each pass takes the last token, runs it through the transformer using the KV cache for context, gets a logit vector, applies temperature and top-p, samples a token, decodes it to a string, prints it, and adds it to the context. Repeat until the model outputs the end-of-sequence token or you hit your limit.

That loop is the whole thing.

What I Actually Learned

A few things that surprised me doing this:

Quantization quality held up better than I expected. At Q4, the output was noticeably worse on tricky reasoning tasks but basically indistinguishable on straightforward Q&A. The size reduction is worth it for most use cases.

Sampling settings matter more than I thought. Temperature 1.0 made Qwen3 0.6B noticeably rambling. Dropping to 0.7 tightened it up. Small adjustments made a real difference in output quality.

The KV cache is where the memory goes. Not the weights, the cache. Long contexts eat memory fast and that’s the real constraint at runtime.

The 0.6B model has clear limits. It trips up on anything requiring multi-step reasoning or broad knowledge. But that actually makes it useful for understanding how these things work, because the failures are obvious and easy to trace.

Closing Thoughts

Writing this from scratch in C took longer than expected and taught me more than any tutorial I’ve read. There’s something different about stepping through a forward pass in a debugger versus reading about transformers in theory. The theory makes sense abstractly. The debugger makes it real.

If you want to try something similar, llama.cpp is the practical starting point. It handles all of this correctly and the code is readable. Even just reading through it will teach you a lot.

The 0.6B model is a good size for this kind of project. Small enough to run anywhere, large enough to actually work.
