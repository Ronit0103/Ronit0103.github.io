So I recently started learning Git and honestly it was a bit overwhelming at first. There are a lot of commands and concepts thrown at you all at once. But once things started clicking, I realised how powerful it actually is. This post is just me writing down what I learned in the order it made sense to me.

What is Git?

Git is basically a tool that tracks changes to your code over time. Every time you save a change in Git, it remembers it. So if you ever break something, you can go back to when things were working.
I like to think of it as a really detailed undo button for your entire project.

Cloning a Project

The first thing I actually did in a real project was clone a repository. Cloning just means downloading a project from somewhere like GitHub onto your own computer.

Adding and Committing

This one confused me for a while. Saving a file in your editor doesn’t save it in Git. You have to do it yourself in two steps. First you add the files you want to save. This is like picking up the things you want to pack. Then you commit, which is like actually sealing the box and labelling it. The label is your commit message, and writing a good one matters a lot. Something like “fixed the login button on mobile” is so much more useful than “fixed stuff” when you’re looking back weeks later. I started committing more often once I understood this.

Small commits with clear messages make everything easier to follow.

Branches

This is the part that made the biggest difference for me. A branch is basically its own separate version of the project where you can make changes without touching the main code. So if I want to try building a new feature, I make a branch, work on it there, and the main project stays completely untouched the whole time. If the feature works out, I merge it back in. If it doesn’t, ’I just delete the branch and nothing is lost. It felt a bit weird at first but now I can’t imagine working without it.

Conflict Resolution

When two people change the same part of the same file on different branches and then try to merge, Git doesn’t know which version to keep. So it flags it as a conflict and asks you to sort it out yourself. It looks a bit scary the first time but it’s actually Git being helpful. It shows you both versions side by side and you just decide what the final version should look like. Once I stopped panicking and just read what Git was showing me, it made total sense.

Keeping Main Safe

The main branch is basically your live, working version of the project. The thing people actually use. So you never want to work directly on it and risk breaking something. The way it works is you always branch off, do your work, get it reviewed if you’re working with others, and only merge it into main once you’re sure it’s good. This keeps main stable and deployable at all times. It’s a simple rule but it changes everything about how confidently you can work.

Collaboration and History

One of the things I didn’t expect to appreciate so much is the history Git keeps. Every commit from every person on the team is saved forever. You can see exactly what changed, who changed it, and why they said they changed it. This is really useful when something breaks. Instead of guessing, you can just look back through the history and find the exact commit that caused the problem. And if you need to undo it, you can do that without touching anything else.

Final Thoughts

Git felt complicated when I first started but a lot of that was just unfamiliarity. The ideas behind it are actually pretty straightforward once you get past the commands. Make small commits, work on branches, keep main clean, and write decent commit messages. That’s most of it honestly.
